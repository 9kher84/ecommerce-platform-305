# P2.2 Optimization Plan: Addressing High Latency

## 🎯 Objective

Reduce p95 latency from ~1.2s to <200ms and improve throughput stability.

## 🔍 Root Cause Analysis (from Baseline 2.0)

The diagnostic tests showed:

- **Success:** 100% (after fixing Rate Limit).
- **Latency:** ~1.2s (p95) for basic health checks.
- **Resource Usage:** Moderate memory increase (4MB delta), indicating no massive leaks, but inefficiency.

Hypothesis: The high latency is driven by **Application Overhead** (Middleware chain) and **Database Latency** (lack of caching).

## 🛠️ Action Items

### 1. Redis Caching (Priority: Critical)

- **Implement:** `redis` caching layer for high-read endpoints.
- **Targets:** Public feeds, User profiles, Metadata.
- **Strategy:** Cache-Aside with 60s TTL for lists.

### 2. Monitoring & Observability

- **New Endpoint:** `/api/health/advanced` (Implemented, pending restart).
- **Metrics:** Add `prom-client` to export metrics for Prometheus.

### 3. Database Optimization

- **Verify Indexes:** Ensure the 8 new indexes are being used (EXPLAIN ANALYZE).
- **Connection Tuning:** Monitor `pg_stat_activity` under load.

## 📅 Execution Plan

1.  **Start Redis:** Ensure local Redis is running.
2.  **Code Caching Layer:** Implement `cacheService.js` wrapper.
3.  **Apply to Endpoints:** Wrap `requestController.js` logic.
4.  **Re-Run Baseline:** Measure improvement (Target: <200ms).
