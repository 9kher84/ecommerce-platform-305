# SOVEREIGN UNSEALING PROTOCOL (SUP-v1)
## CLASSIFICATION: TOP SECRET / COMMAND EYES ONLY

### 1. Emergency Condition
Unsealing the system is permitted ONLY under the following conditions:
- Critical Security Vulnerability (CVSS > 9.0)
- Sovereign Schema Upgrade (Authorized by Command)
- Total System Failure requiring core intervention

### 2. The 3-Key Authorization Process
To lift the Read-Only Sovereign Seal, three distinct keys/approvals are required:

1.  **Technical Key**: Logical access to the server with Administrator privileges.
2.  **Compliance Key**: A unique audit token generated by `backend/services/auditService` flagging an "EMERGENCY_UNSEAL" event.
3.  **Command Key**: Written authorization from the Project Owner referencing the specific Change Request (CR) ID.

### 3. Execution Sequence (The "Unsealing")

**Step 1: Declare Emergency in Audit Log**
```javascript
// Run via console
const audit = require('./services/auditService');
audit.logSecurityAlert('OWNER', 'EMERGENCY_UNSEAL_INITIATED', 'CR-2025-X');
```

**Step 2: Lift OS Attribute**
```powershell
attrib -R backend/core /S /D
attrib -R backend/sequelize_setup.js
```

**Step 3: Execute Modification**
- Perform minimal necessary changes.
- NO feature creep allowed.

**Step 4: Verify & Reseal**
1. Run `npm test` to ensure stability.
2. Run `node backend/scripts/sovereign_seal.js` to:
   - Recalculate Hashes.
   - Update `.sovereign_snapshot.json`.
   - Re-apply `+R` (Read-Only) attribute.

### 4. Post-Incident Review
Within 24 hours of unsealing, a "Sovereign Incident Report" must be filed, detailing:
- Duration of unsealed state.
- Exact lines of code changed.
- Diff of `.sovereign_snapshot.json` before and after.

---
**WARNING:** Any unsealing event not followed by a Reseal within 4 hours is considered a Hostile Takeover.
